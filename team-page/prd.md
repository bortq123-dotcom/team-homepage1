# 에이또팀 팀 소개 페이지 PRD

| 항목 | 내용 |
|---|---|
| 문서 상태 | v1.0 · 구현 완료 · 로컬 HTTP 브라우저 확인 완료 |
| 작성일 | 2026-11-06 |
| 작성 기준 | 사용자 인터뷰 답변 · 제공된 디자인 MD · team-page-prd 템플릿 |
| 관련 문서 | logo-prompt.md, image-prompt.md, build-plan.md, verification.md |

> PRD는 무엇을, 누구를 위해, 왜 만드는지를 정리한 제품 요구사항 문서입니다. 사용자 제공 디자인 MD를 반영한 홈페이지 구현과 로컬 HTTP 환경의 브라우저 확인을 마쳤습니다. 실제 `file://` 실행과 JavaScript 비활성화 브라우저 실험은 수행하지 않았습니다. 확인 결과는 `verification.md`에 기록했습니다.

## 1. 배경 · 문제

- 에이또팀은 안전서류 작업을 담당하며, 이번 홈페이지에서는 **작업계획서 작성 요청**을 다룹니다.
- 주 사용자는 팀원입니다. 팀 소개와 요청 가능한 서류를 확인한 뒤 홈페이지 신청폼을 사용합니다.
- 이번 목표는 **화면과 입력 흐름을 먼저 체험**하는 것입니다. 실제 담당자에게 요청을 전달하는 기능은 후속 범위입니다.
- 요청 항목을 화면에서 한 번에 정리하면 입력 흐름을 이해하기 쉽다는 점을 기획의 출발점으로 삼습니다. 현재 업무의 구체적인 불편 사항이나 운영 성과는 조사하지 않았습니다. `(가정)`

## 2. 목표와 성공 기준

| 목표 | 성공 기준 · 확인 방법 |
|---|---|
| 팀원이 에이또팀의 역할과 이번 지원 서류를 이해한다 | 첫 화면과 업무 카드에서 안전서류 작업 및 작업계획서 작성 요청을 확인할 수 있음 |
| 신청폼 입력 흐름을 끝까지 체험한다 | 입력 → 내용 확인 → 수정 또는 체험 완료 → 다시 작성이 동작함 |
| 입력 오류를 스스로 수정할 수 있다 | 필수 항목 누락 시 항목 가까이에 오류가 표시되고 첫 오류 항목으로 포커스가 이동함 |
| 체험 결과를 실제 접수와 구별할 수 있다 | 폼 시작 부분과 완료 화면에 입력 체험임을 표시하고, 담당자 전달·접수 완료로 표현하지 않음 |
| 휴대폰에서도 편하게 입력한다 | 375px 폭에서 가로 스크롤이 없고 입력 항목과 버튼을 사용할 수 있음 |

## 3. 대상 사용자

| 대상 | 궁금한 것 | 페이지가 줘야 할 답 | 기대 행동 |
|---|---|---|---|
| 에이또팀 팀원 | 팀이 어떤 안전서류 작업을 하는지, 작업계획서 작성을 어떻게 요청하는지 | 팀 역할, 지원 서류, 요청 입력 항목과 검토 흐름 | 신청폼에 예시 내용을 입력하고 검토·수정·체험 완료까지 진행 |

## 4. 범위

**이번에 만드는 것**

- 로고와 팀 소개, 작업계획서 업무 카드, 도구 준비 중 카드, 작성 요청 체험폼이 있는 한 장짜리 홈페이지.
- 새 로고 `images/logo.png`. 한글 워드마크와 접힌 문서·체크 아이콘을 사용한 로고 초안을 생성하고 시각적으로 확인했습니다.
- 사진 중심의 넓은 히어로에 생성 이미지 `images/hero-workplan.png`를 적용했습니다. 작업대 위 문서를 함께 살펴보는 장면입니다.
- 신청 내용 입력, 필수 항목 확인, 검토 화면, 수정, 체험 완료, 다시 작성.
- 데스크톱과 휴대폰 대응, 키보드 입력과 오류 안내.
- 입력값은 현재 열린 화면의 메모리에서만 유지합니다. 새로고침하면 초기화됩니다. `(가정)`

**이번에 만들지 않는 것**

- 실제 담당자 전달, 이메일 발송, 서버 저장, 팀 공용 요청 목록, 로그인, 파일 첨부.
- 작업계획서 본문 자동 작성이나 안전 작업 절차·법규 검토.
- 인터뷰에서 확인하지 않은 다른 서류 서비스, 실제 멤버 정보, 성과 수치.

| 메뉴 | 섹션 ID | 담는 내용 |
|---|---|---|
| 팀 소개 | `#intro` | 에이또팀 역할, 팀원을 위한 안내, 작성 요청 체험 시작 버튼 |
| 작성 가능한 서류 | `#work` | 작업계획서 작성 요청 카드 1개 |

메뉴는 대화에서 제안한 기본 구성을 적용한 초안입니다. `(가정)`

## 6. 화면 구성 · 위에서 아래로

```text
[고정 헤더: 에이또팀 로고 + 메뉴]
① 팀 소개: 넓은 사진 히어로 / 큰 제목 / 보조 문구 / [작성 요청 체험하기]
② 작성 가능한 서류: 작업계획서 카드 1개
③ 우리가 만든 도구: 준비 중 카드
④ 작성 요청: 입력 체험 안내 + 단계 표시 + 신청폼
[푸터: 에이또팀 / 작업계획서 작성 요청 입력 체험]
```

첫 화면은 모서리 없는 넓은 사진과 크게 대비되는 타이포그래피를 중심으로 구성합니다. 본문과 폼은 중성 색의 단정한 화면으로 이어집니다. 업무 종류가 1개이므로 다른 서비스를 추가해 카드 수를 늘리지 않습니다.

## 7. 콘텐츠 상세

### 7-1. 한 줄 소개

- 제목: **작업의 시작, 계획부터.** `(인터뷰를 바탕으로 작성한 문구)`
- 보조 문구: “안전서류 작업을 담당하는 에이또팀. 팀원의 작업계획서 작성 요청을 함께 준비합니다.”
- 버튼: **작성 요청 체험하기** → `#request`.
- 팀 역할: “에이또팀은 안전서류 작업을 담당합니다.”

### 7-2. 업무 카드

| 제목 | 설명 | 요청 예시 |
|---|---|---|
| 작업계획서 | 작업계획서 작성을 요청하기 위한 기본 내용을 정리합니다. | “예정된 작업의 계획서 작성을 요청하고 싶어요.” `(가정 · 예시)` |

카드 버튼은 “입력 체험하기”로 표시하고 신청폼으로 이동합니다.

### 7-3. 작성 요청 체험폼

아래 입력 항목과 필수 여부는 인터뷰에서 확정하지 않은 **체험용 초안**입니다. `(가정)`

| 항목 | 필수 | 입력 방식 | 안내 · 확인 |
|---|---|---|---|
| 닉네임 | 필수 | 짧은 텍스트 | 예: 팀원A. 공백만 입력하면 오류 |
| 작업명 | 필수 | 짧은 텍스트 | 예: 가상 작업 A. 공백만 입력하면 오류 |
| 가상 작업구역 | 필수 | 짧은 텍스트 | 예: 샘플 구역 A. 공백만 입력하면 오류 |
| 작업 예정일 | 필수 | 날짜 선택 | 날짜 형식의 유효한 값인지 확인. 임의의 안전·법규상 기한을 적용하지 않음 |
| 요청 내용 | 선택 | 여러 줄 텍스트 | 예시 요청 사항을 자유롭게 입력 |

**입력 단계**

- 상단에 “작업계획서 작성 요청 · 입력 체험”을 표시합니다.
- 안내 문구: “예시 내용으로 입력 흐름을 체험해 보세요. 입력한 내용은 담당자에게 전달되지 않으며 새로고침하면 사라집니다.”
- 버튼: **내용 확인**.
- **예시로 채워보기** 버튼으로 빈 폼에 체험용 값을 넣을 수 있습니다. 입력 중인 값이 있으면 기존 값을 유지합니다.
- 값은 앞뒤 공백을 정리해 검토 화면에 표시합니다.
- 오류가 있으면 항목별 오류 문구를 표시하고 첫 오류 항목으로 포커스를 옮깁니다. 오류는 색과 문구로 함께 구분합니다.

**검토 단계**

- 입력한 내용을 항목명과 함께 읽기 쉽게 표시합니다. 선택 항목이 비어 있으면 “입력하지 않음”으로 표시합니다.
- 사용자 입력은 HTML로 해석하지 않고 텍스트로 표시합니다.
- 버튼: **수정하기**, **체험 완료**.
- 수정하기를 누르면 입력값을 유지한 채 입력 단계로 돌아갑니다.

**완료 단계**

- 제목: **입력 체험을 마쳤습니다**.
- 설명: “작업계획서 작성 요청 흐름을 확인했습니다. 실제 요청은 전달되지 않았습니다.”
- 버튼: **다시 작성하기**. 누르면 입력값과 오류 상태를 지우고 첫 입력 항목으로 이동합니다.
- 단계가 바뀔 때 해당 단계 제목으로 포커스를 옮기고 보조기기에 변화를 알립니다.

### 7-4. 우리가 만든 도구

- 도구 카드 1개에 **준비 중**을 표시합니다.
- 실제 도구명이나 출시 일정을 약속하는 문구는 넣지 않습니다.

## 8. 디자인 가이드

사용자가 제공한 `붙여넣은 텍스트.txt`의 사진 중심 구성과 큰 타이포그래피 대비를 에이또팀 콘텐츠에 적용합니다. 참고자료의 Nike 로고·상품·독점 글꼴은 사용하지 않습니다.

| 항목 | 값 |
|---|---|
| 메인 색 | 잉크 블랙 `#111111` · 제목, 본문, 주요 버튼 |
| 보조 색 | 흰색 `#FFFFFF`, 옅은 회색 `#F5F5F5` · 화면과 구획 배경 |
| 포인트 색 | 기존 로고의 틸만 유지. 버튼·폼·메뉴는 중성 색 사용 |
| 느낌 | 깔끔한 / 사진 중심 / 분명한 크기 대비 |
| 글꼴 | 로컬 `fonts/PretendardVariable.woff2` · SIL Open Font License. 라이선스는 `fonts/LICENSE.txt`에 포함. 외부 글꼴 CDN 없음 |
| 글자 위계 | 히어로 제목 데스크톱 약 80~112px·모바일 약 48px, 본문 16px 안팎. 한글 가독성에 맞춰 행간 조절 `(세부 크기 가정)` |
| 간격 | 8px을 기본으로 16·24·32·48·64px 리듬 사용 |
| 사진 · 카드 | 모서리 0, 평평한 구획, 필요한 곳에 얇은 경계선 사용 |
| 버튼 | `#111111` 배경·흰 글자의 pill 형태. 보조 버튼은 연회색 |
| 그림자 · 장식 | 그림자와 장식 그라데이션 최소화. 사진이 화면의 깊이를 담당 |
| 로고 | 기존 `images/logo.png` 유지 · 생성 및 시각 확인 완료 |
| 히어로 사진 | `images/hero-workplan.png` · 생성 및 적용 완료 |
| 디자인 참고 | 사용자 제공 디자인 MD `붙여넣은 텍스트.txt` |

큰 제목은 히어로에 집중하고, 아래 업무 안내와 폼은 읽기 편한 작은 글자 위계로 정리합니다. 사진 위 글자는 배경과 충분히 구별되게 배치하며 실제 텍스트로 제공합니다.

## 9. 반응형 · 접근성

- 휴대폰 375px와 데스크톱 1280px에서 가로 스크롤 없이 표시합니다.
- 데스크톱 히어로는 넓은 가로 사진, 휴대폰은 세로에 가까운 크롭으로 조정합니다. 사진의 주요 장면과 제목이 함께 보이도록 위치를 조절합니다.
- 640px 아래에서 메뉴를 햄버거 버튼으로 전환합니다. 열림 상태와 버튼 이름을 보조기기에 제공합니다.
- 모바일 좌우 여백은 16px 이상을 확보하고 입력폼은 1열로 유지합니다.
- 입력 항목에는 항상 보이는 라벨을 연결합니다. 필수 여부를 문구로 표시하고 오류 설명을 해당 입력과 연결합니다.
- 키보드 포커스를 분명히 표시하고 단계 전환·오류 발생 후에도 조작 위치를 알 수 있게 합니다.
- 로고에 “에이또팀” 대체 텍스트를 제공합니다. 로고 옆에 같은 팀 이름이 반복되면 장식 이미지로 처리해 중복 낭독을 피합니다.
- 고정 헤더가 섹션 제목을 가리지 않도록 이동 위치에 여백을 둡니다.

## 10. 기술 조건

- `index.html` 한 파일에 CSS와 JavaScript를 포함합니다. 사진은 `images/`, 글꼴은 `fonts/`의 상대경로 로컬 파일을 참조합니다.
- 빌드 도구와 서버 API가 필요 없는 구조입니다. 폴더를 유지한 채 `index.html`을 더블클릭해 사용하는 형태로 준비했으며, 실제 `file://` 브라우저 동작은 미확인입니다.
- 폼 상태는 현재 페이지의 JavaScript 메모리에서만 관리합니다. `(가정)`
- 폼 처리는 페이지 안에서 수행하고 제출에 따른 네트워크 요청을 만들지 않습니다.
- 초기 HTML의 폼 `fieldset`을 비활성화하고 모든 이벤트 핸들러 연결 후 활성화합니다. JavaScript 초기화 전 기본 폼 제출을 막는 코드 보완이며, JavaScript 비활성화 환경의 브라우저 실험은 미수행입니다.
- 저장 기능, 외부 서비스 연결, 브라우저 장기 저장을 추가할 때는 후속 요구사항으로 별도 정리합니다.

- [x] 로고·히어로 이미지 로드와 도구의 “준비 중” 표시를 확인했다.

## 13. 열린 질문

- 디자인은 사용자 제공 MD를 반영했고 데스크톱·모바일 화면을 확인했습니다. 추가 피드백이 있으면 글자 크기와 사진 크롭을 조정할 수 있습니다.
- 기본 메뉴 구성은 기존 기획의 가정으로 유지하며 필요하면 수정할 수 있습니다.
- 닉네임·작업명·가상 작업구역·예정일·요청 내용 및 필수 여부는 체험용 가정입니다. 실제 운영 항목으로 확정하지 않았습니다.
- 현재 페이지 메모리에서만 값을 유지하고 새로고침 시 초기화하는 방식은 체험 범위에 맞춘 가정입니다.
- 실제 `file://` 실행과 JavaScript 비활성화 브라우저 실험은 추가 확인 항목입니다.
- 실제 담당자 전달이나 팀원 간 공동 확인이 필요해지면 수신 방식과 저장 위치를 후속 단계에서 정합니다.
